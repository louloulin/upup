# Internationalization (i18n)

> **UpUp is bilingual out of the box** — English + Simplified Chinese. All user-facing strings are centralized in a single strongly-typed table. Adding a new key in only one locale fails the build.

---

## Why a Custom (Tiny) i18n System?

We deliberately do **not** use `i18next` / `react-intl` / `vue-i18n`:

- **Single source of truth** — one `strings.ts` file, easy to grep
- **Strongly typed keys** — typos fail at compile time
- **Symmetry enforced by tests** — missing `zh-CN` for an `en` key fails CI
- **Hermetic** — no third-party dependencies, no polyfills, ~100 LOC total
- **Default to user's language** — `LANG` / `LC_ALL` env vars, override with `UPSTREAM_LOCALE`

## Using a String

```ts
import { t, getLocale } from '../i18n/strings.js';

// At runtime, resolves to current locale
const title = t('intro.welcome');  // "涨涨 · 深度金融研究 AI" (if zh-CN)
```

In a React (Ink) component:

```tsx
import { useLocale, t } from '../i18n/strings.js';

export function Intro() {
  const locale = useLocale();
  return <Text>{t('intro.welcome')}</Text>;
}
```

## Locale Detection

```ts
// src/i18n/locale.ts
export function getLocale(): Locale {
  if (process.env.UPSTREAM_LOCALE) {
    return process.env.UPSTREAM_LOCALE as Locale;
  }
  const env = process.env.LANG || process.env.LC_ALL || 'en_US.UTF-8';
  if (env.startsWith('zh')) return 'zh-CN';
  return 'en';
}
```

Override at runtime:

```bash
UPSTREAM_LOCALE=zh-CN bun start
UPSTREAM_LOCALE=en bun start
```

## Adding a New Key

1. **Add to `StringKey` type** (compile-time check)
2. **Add to `en` block** (English string)
3. **Add to `zh-CN` block** (Chinese string)
4. **Add a unit test** if the key is user-facing

```ts
// src/i18n/strings.ts
export type StringKey =
  | /* ... existing ... */
  | 'risk.warning';  // ← new

export const strings = {
  en: {
    /* ... existing ... */
    'risk.warning': 'Warning: this strategy has not been backtested.',
  },
  'zh-CN': {
    /* ... existing ... */
    'risk.warning': '警告：此策略尚未回测。',
  },
};
```

The test in `src/i18n/strings.test.ts` will fail if you add a key in only one locale.

## Adding a New Locale

To add (e.g.) Japanese:

1. Add `'ja'` to `Locale` type and `SUPPORTED_LOCALES`
2. Add a `ja` block in `strings` — must contain **every** key in `StringKey`
3. Add a `getLocale()` rule for `'ja.*'`
4. Add a test asserting the symmetry
5. Add Japanese translations for every prompt / skill description

We're happy to accept PRs for additional locales — see [CONTRIBUTING.md](../CONTRIBUTING.md#translation--i18n).

## Skill Descriptions

Skill descriptions in `SKILL.md` frontmatter are **not** in the i18n table — they're read directly by the LLM. We recommend:

- **English first** (most LLMs are best at English)
- **Add Chinese keywords** in the description field (for routing when user is Chinese)

```yaml
---
name: dcf
description: >
  DCF / Discounted Cash Flow / 现金流折现 / 公司估值. Use this skill for
  fundamental valuation of a single company with predictable cash flows.
---
```

This way, the LLM can match both English and Chinese queries.

## Prompt Strings

Long prompt templates live in `src/agent/prompts.ts` and `src/agent/prompts.locale.test.ts`. We keep English as the canonical version (LLM reasoning is best in English) and use locale-specific overlays for tone:

```ts
// src/agent/prompts.ts
export const IDENTITY = {
  en: 'You are UpUp, a financial research agent…',
```

## Component Strings

All Ink TUI components use the `t()` helper. The sweep in P3.a.3 brought 5 components and 19 new keys under i18n.

```ts
// src/components/StatusLine.tsx
import { t } from '../i18n/strings.js';

export function StatusLine() {
  return <Text>{t('status.pnl_today', { pnl: '+1.2%' })}</Text>;
}
```

Interpolation uses `{name}` placeholders:

```ts
strings['en']['status.pnl_today'] = 'Today P&L: {pnl}';
strings['zh-CN']['status.pnl_today'] = '今日盈亏：{pnl}';

t('status.pnl_today', { pnl: '+1.2%' })  // → "今日盈亏：+1.2%"
```

## Testing

```ts
// src/i18n/strings.test.ts
import { describe, it, expect } from 'bun:test';
import { strings, SUPPORTED_LOCALES, type StringKey } from './strings.js';

describe('i18n', () => {
  it('has all locales for all keys', () => {
    for (const locale of SUPPORTED_LOCALES) {
      for (const key of Object.keys(strings.en) as StringKey[]) {
        expect(strings[locale][key]).toBeDefined();
        expect(strings[locale][key].length).toBeGreaterThan(0);
      }
    }
  });

  it('no extra keys in non-default locales', () => {
    for (const locale of SUPPORTED_LOCALES) {
      if (locale === 'en') continue;
      const extra = Object.keys(strings[locale]).filter(
        k => !(k in strings.en),
      );
      expect(extra).toEqual([]);
    }
  });
});
```

Run: `bun test src/i18n/`

## Anti-Patterns

- ❌ Hardcoded strings in components
- ❌ Using a third-party i18n library
- ❌ Translating only the visible string (forget the error message, fail silently)
- ❌ Translating code comments (keep them English — they're for developers)
- ❌ Translating skill bodies (LLMs reason best in English; keep canonical)
